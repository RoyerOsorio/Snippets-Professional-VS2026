# Objetivo

Tienes acceso al proyecto actual de UI de **Multiportal Reembolsos**, desarrollado con **ASP.NET Core MVC, C# y Razor**.

Necesito que construyas sobre este proyecto un **ejercicio técnico empresarial completo y ejecutable de arquitectura de microservicios**, cuyo propósito principal es demostrar de extremo a extremo cómo funcionará la nueva arquitectura.

Este desarrollo será utilizado como **demo técnico para el gerente y para el equipo de desarrollo**, por lo que debe permitir observar claramente:

* cómo está estructurado el repositorio;
* cómo se separan las soluciones y proyectos;
* cómo se comunica la UI con el backend;
* cuál es el papel del API Gateway;
* cuál es el papel del Orchestrator;
* cómo se comunican los microservicios;
* qué lógica pertenece a cada microservicio;
* cómo cada microservicio accede exclusivamente a su propia base de datos;
* cómo se utilizan llamadas síncronas HTTP;
* cómo se utilizan eventos asíncronos mediante RabbitMQ;
* cómo fluye una operación desde Razor hasta SQL Server;
* cómo puede consultarse posteriormente desde la UI el resultado del proceso.

No busco solamente pseudocódigo o documentación.

**Debes crear código real, estructura real de soluciones/proyectos, configuración, scripts y componentes ejecutables.**

---

# Estrategia de base de datos: Database First

El proyecto utilizará:

**SQL Server + Entity Framework Core + Database First.**

No utilices Code First como estrategia principal.

Las bases y tablas representan un esquema existente que debe ser tratado como fuente de verdad para persistencia.

Debes:

1. analizar los `.txt` proporcionados;
2. identificar las tablas necesarias para este vertical slice;
3. crear o preparar los scripts SQL necesarios para montar localmente esas estructuras en SQL Server;
4. utilizar `Scaffold-DbContext` / `dotnet ef dbcontext scaffold` o una estrategia equivalente de EF Core Database First;
5. generar las entidades de persistencia y `DbContext` desde la base;
6. mantener el código generado por scaffold separado de la lógica de dominio;
7. evitar colocar comportamiento de dominio directamente en las entidades generadas automáticamente.

Ejemplo conceptual:

```text
SQL Server
    ↓
EF Core Database First
    ↓
Entidades de persistencia generadas
    ↓
Adaptadores / Infrastructure
    ↓
Application / Domain
```

No conviertas automáticamente las entidades generadas por Database First en entidades de dominio ricas.

Debe existir una separación clara entre:

```text
Modelo de persistencia
≠
Modelo de dominio
```

cuando el caso de uso realmente requiera comportamiento de dominio.

# Regla importante sobre scaffolding

El código generado mediante Database First puede regenerarse.

Por ello:

* evita modificar directamente archivos generados cuando sea posible;
* utiliza partial classes cuando realmente sea necesario extender una entidad generada;
* utiliza mappers/adapters hacia el dominio;
* documenta cómo volver a ejecutar el scaffold;
* documenta qué archivos son generados y cuáles son escritos manualmente.

Crea scripts o instrucciones reproducibles, por ejemplo:

```bash
dotnet ef dbcontext scaffold \
    "<cadena-conexion>" \
    Microsoft.EntityFrameworkCore.SqlServer \
    --context MprClientesDbContext \
    --output-dir Persistencia/ModelosGenerados \
    --context-dir Persistencia \
    --no-onconfiguring \
    --force
```

Ajusta los nombres y parámetros a la estructura real.

No expongas contraseñas reales en Git.

# Principios arquitectónicos obligatorios

Implementa los microservicios siguiendo:

* **SOLID**;
* **Clean Architecture pragmática/híbrida**;
* **Ports & Adapters / Hexagonal Architecture**;
* **Minimal APIs** como adaptador HTTP.

La arquitectura debe ser pragmática.

No introduzcas capas, interfaces, repositories, factories o abstracciones si no aportan valor concreto al caso de uso.

Evita diseño ceremonial o sobrearquitectura.

---

# Clean Architecture híbrida

Utiliza aproximadamente:

```text
Api
    ↓
Application
    ↓
Domain

Infrastructure
    ├──→ Application
    └──→ Domain
```

La regla principal es:

**Domain debe permanecer independiente de infraestructura y frameworks.**

El proyecto Domain NO debe depender de:

* Infrastructure;
* ASP.NET Core;
* Entity Framework Core;
* SQL Server;
* RabbitMQ;
* clientes HTTP;
* YARP;
* Azure API Management.

---

# SOLID

Aplica SOLID de forma pragmática.

Especialmente:

## Single Responsibility

Cada componente debe tener una responsabilidad claramente identificable.

## Open/Closed

Permite sustituir adapters cuando tenga sentido sin modificar los casos de uso.

## Liskov Substitution

Las implementaciones deben respetar correctamente sus contratos.

## Interface Segregation

Prefiere interfaces pequeñas y orientadas a capacidades.

## Dependency Inversion

Application/Domain no deben depender directamente de detalles externos.

# Minimal APIs

Utiliza Minimal APIs para los microservicios.

Los endpoints deben ser delgados.

Ejemplo:

```csharp
grupo.MapPost(
    "/{reclamoId:guid}/aprobar",
    AprobarReclamoAsync);
```

```csharp
private static async Task<IResult> AprobarReclamoAsync(
    Guid reclamoId,
    AprobarReclamoManejador manejador,
    CancellationToken cancellationToken)
{
    var resultado = await manejador.ManejarAsync(
        new AprobarReclamoComando(reclamoId),
        cancellationToken);

    return Results.Ok(resultado);
}
```

No coloques 100 o 200 líneas de lógica dentro del endpoint.

Organiza los endpoints por feature, por ejemplo:

```text
MprGestionReclamos.Api/
│
├── Endpoints/
│   └── Reclamos/
│       ├── CrearReclamoEndpoint.cs
│       ├── EnviarReclamoEndpoint.cs
│       ├── AprobarReclamoEndpoint.cs
│       └── ObtenerReclamoEndpoint.cs
│
├── Extensiones/
│   ├── ExtensionesServicios.cs
│   └── ExtensionesEndpoints.cs
│
└── Program.cs
```

Mantén `Program.cs` pequeño.

# Regla fundamental sobre microservicios

Cada microservicio debe:

* poseer su lógica de negocio;
* poseer su modelo;
* poseer exclusivamente su propia base SQL Server;
* acceder solamente a su base;
* publicar contratos explícitos;
* comunicarse con otros servicios mediante API o eventos.

Está prohibido:

* consultar directamente la base de datos de otro microservicio;
* crear foreign keys entre bases de diferentes microservicios;
* hacer JOIN entre bases de microservicios;
* crear stored procedures distribuidos;
* compartir `DbContext`;
* utilizar una base común;
* colocar toda la lógica de negocio en el Orchestrator.

---

# Responsabilidad del Orchestrator

Debe existir:

`Reimbursement.Orchestrator`

Su función es:

**coordinar procesos de aplicación que involucren varios microservicios.**

El Orchestrator puede conocer:

* qué pasos deben ejecutarse;
* en qué orden;
* a qué servicio debe invocar;
* cómo manejar una respuesta;
* cómo continuar el proceso.

El Orchestrator NO debe conocer internamente:

* cómo se determina una vigencia;
* cómo se calcula una regla propia de MprConfiguracionReglas;
* cómo se valida internamente un Reclamo;
* cómo se valida un documento;
* cómo se ejecuta internamente un pago.

Regla:

> El Orchestrator posee la lógica de coordinación; cada microservicio posee las reglas e invariantes de su dominio.

---

# Responsabilidad del API Gateway

* routing;

* rate limiting cuando aplique.

NO debe contener lógica de negocio.

NO debe convertirse en un Orchestrator.

# Flujo de negocio a implementar

Implementa un **happy path completo de registro y procesamiento de un reembolso**.

Debe atravesar realmente la arquitectura.

---

# Paso 1 — Seleccionar cliente

Desde Razor:

* consultar clientes;
* seleccionar uno;
* mostrar datos básicos;
* mostrar póliza;
* mostrar certificado;
* mostrar vigencia.

Flujo:

```text
UI
↓
Gateway
↓
MprClientes
↓
SQL Server MprClientes
```

---

# Paso 2 — Iniciar reembolso

La UI solicita crear un reembolso.

Flujo:

```text
UI
↓
Gateway
↓
Reimbursement.Orchestrator
```

El Orchestrator debe:

1. consultar `MprClientes`;
2. obtener/verificar contexto contractual;
3. consultar `MprConfiguracionReglas`;
4. obtener reglas;
5. obtener documentos requeridos;
6. solicitar a `MprGestionReclamos` crear el Reclamo;
7. solicitar a `MprDocumentos` preparar/asociar documentos.

---

# El Orchestrator no ejecuta reglas internas

Evita:

```csharp
if (fechaActual <= fechaFinPoliza)
{
    ...
}
```

dentro del Orchestrator si esa regla pertenece a `MprClientes`.

En cambio utiliza una operación explícita del servicio correspondiente.

Ejemplo conceptual:

```text
ValidarContextoCliente
```

Lo mismo aplica para reglas de reembolso.

* ReclamoId;

* MotivoReembolsoId;

* fecha;
* datos mínimos requeridos.

`MprDocumentos`:

* asocia documentos requeridos;
* permite subir al menos un archivo;
* almacena metadata en SQL Server;
* almacena el archivo externamente/localmente;
* mantiene estado documental.

Implementa:

# Transacciones ACID locales

Cada microservicio debe manejar **transacciones ACID locales mediante EF Core + SQL Server**.

Las operaciones que modifiquen varias entidades o registros dentro de la misma base deben ejecutarse atómicamente mediante:

* BEGIN TRANSACTION;
* COMMIT;
* ROLLBACK.

No implementes transacciones distribuidas entre microservicios.

Ejemplo conceptual:

```text
AprobarReclamo

BEGIN TRANSACTION

Actualizar Reclamo
Insertar información relacionada
Insertar mensaje Outbox

COMMIT
```

Si falla alguno:

```text
ROLLBACK
```

---

# Uso de SaveChanges y transacciones explícitas

Cuando una sola llamada a:

```csharp
SaveChangesAsync()
```

sea suficiente para garantizar atomicidad local, aprovecha el comportamiento transaccional de EF Core.

Cuando el caso de uso requiera:

* múltiples `SaveChangesAsync`;
* operaciones explícitas intermedias;
* control transaccional específico;
* múltiples modificaciones que necesiten delimitar claramente la unidad atómica;

utiliza:

```csharp
await dbContext.Database.BeginTransactionAsync(...)
```

y maneja:

```csharp
CommitAsync()
RollbackAsync()
```

de forma explícita.

No agregues transacciones explícitas innecesarias.

---

# Consistencia entre microservicios

Está prohibido intentar algo semejante a:

```text
BEGIN DISTRIBUTED TRANSACTION

MprClientes DB
MprGestionReclamos DB
MprDocumentos DB
MprPagos DB

COMMIT
```

En su lugar utiliza:

```text
Transacciones locales
+
Transactional Outbox
+
Idempotencia
+
Reintentos
+
Consistencia eventual
+
Compensaciones/Saga cuando corresponda
```

---

# Transactional Outbox

Para operaciones que:

1. modifican SQL Server;
2. y generan un evento de integración;

utiliza Transactional Outbox.

Ejemplo:

```text
BEGIN TRANSACTION

Actualizar Reclamo

INSERT OutboxMessage
(
    ReclamoAprobadoParaPago
)

COMMIT
```

Después:

```text
Procesador Outbox
↓
RabbitMQ
```

No utilices como solución definitiva:

```csharp
await dbContext.SaveChangesAsync();
await rabbitMq.PublicarAsync(evento);
```

sin manejar el escenario donde SQL Server confirma y RabbitMQ falla.

# Saga / compensaciones

Cuando el Orchestrator coordine varios servicios, no utilices rollback SQL remoto.

Ejemplo:

```text
Validar cliente          OK
Obtener reglas           OK
Crear reclamo            OK
Preparar documentos      ERROR
```

El Orchestrator debe decidir entre:

* reintentar;
* mantener el proceso pendiente;
* ejecutar una acción compensatoria;
* marcar el proceso como fallido recuperable.

Si implementas una compensación, utiliza un caso de uso explícito.

Ejemplo:

```text
CancelarReclamoPorFalloDeInicializacion
```

No manipules directamente las tablas de Claims desde el Orchestrator.

# Comunicación síncrona vs asíncrona

Utiliza HTTP cuando:

* se necesita respuesta inmediata;
* el Orchestrator necesita información para continuar;
* la UI solicita una consulta.

Utiliza RabbitMQ cuando:

* se comunica un hecho ocurrido;
* el consumidor puede reaccionar de forma desacoplada;
* no se necesita respuesta inmediata.

# Principios finales obligatorios

No quiero seis CRUD APIs detrás de un Orchestrator inteligente.

Quiero:

```text
Orchestrator
    = coordinación entre servicios

Application
    = casos de uso y puertos

Domain
    = reglas e invariantes

Infrastructure
    = SQL Server + EF Core Database First
      + RabbitMQ + HTTP + Outbox

Minimal APIs
    = adaptadores HTTP delgados

API Gateway
    = frontera, routing y políticas

RabbitMQ
    = integración asíncrona

SQL Server
    = transacciones ACID locales

UI
    = interacción con el usuario
```

Además:

> Cada microservicio debe manejar transacciones ACID locales mediante EF Core y SQL Server. Las operaciones que modifiquen varios datos dentro de la misma base deben ejecutarse atómicamente mediante commit/rollback. No se permiten transacciones distribuidas entre microservicios. Para mantener consistencia entre servicios utiliza Transactional Outbox, idempotencia, reintentos y, cuando el proceso lo requiera, compensaciones/Saga.

Y:

> Implementa los microservicios siguiendo SOLID, Clean Architecture pragmática/híbrida y Ports & Adapters (Hexagonal Architecture). Utiliza Minimal APIs como adaptador HTTP y mantén los endpoints delgados. El Domain no debe depender de Infrastructure, ASP.NET Core, EF Core, RabbitMQ ni clientes HTTP. Application debe definir los puertos necesarios e Infrastructure proporcionar sus adaptadores. No introduzcas capas, repositories, factories o abstracciones si no aportan valor concreto al caso de uso.

Por último:

> Utiliza SQL Server y Entity Framework Core con estrategia Database First. Mantén las entidades generadas de persistencia separadas del modelo de dominio cuando exista comportamiento de negocio. Todo el código propio del proyecto, nomenclatura funcional, comentarios y documentación debe escribirse en español, excepto palabras reservadas y términos técnicos que no sea conveniente traducir.
